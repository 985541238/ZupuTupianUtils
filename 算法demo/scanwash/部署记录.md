```bash

# mask_ratio / angle_deg / size_in / size_out / gutter / review / ms
```

## 六、本次部署踩坑

| 问题 | 原因 | 解决 |
|---|---|---|
| Docker 引擎起不来 | 沙箱安全策略把 `wsl.exe` 拉黑，Docker Desktop 的 Linux 引擎依赖 WSL2 | 用户手动启动 Docker Desktop（其会话不受黑名单限制），引擎就绪后自动继续 |
| `docker build` 报 `auth.docker.io` 502 | 本机网络到 Docker Hub 官方源不可达 | 经 DaoCloud 镜像站拉基础镜像后 `docker tag` 成标准 `python:3.12-slim`，Dockerfile 保持标准写法 |
| 自检 grep 到 `scanwash/webapp.py` 有 127.0.0.1 | 并行开发会话留下的本地网页入口（12:02 出现），默认绑 127.0.0.1 供本地 `python -m scanwash.webapp` 使用 | 非服务入口、镜像内惰性，未删除；服务入口 app.py 绑 0.0.0.0，不受影响 |

> 备注：`scanwash/webapp.py` + `page.html` 与 `_inktry/`（算法实验）是并行会话的在建文件，未动。后续若收敛服务入口，可考虑把 webapp 的本地能力并入 app.py 或明确分工。

## 七、待办 / 风险

1. 单次上传上限 40MB，nginx 侧 `client_max_body_size 100m`，超大扫描页需留意。
2. 服务无并发保护（FastAPI 线程池默认 40），CPU 密集型清洗在大并发下会排队；如需要可加处理锁（webapp.py 里有可参考的 `PROCESS_LOCK` 写法）。
3. 服务器整机内存偏紧（Dify 常驻约 2.6G），scanwash 单页处理峰值约数百 MB，目前余量充足。
4. 并行会话仍在迭代 scanwash 算法（_inktry 实验），算法定版后需重新构建推送并升级版本。
