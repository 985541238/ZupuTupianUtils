## 9.3 使用方式

1. 打开管理端 → 顶部「OCR识别」；
2. **「新建项目」只创建项目**：填名称/姓氏；可选「族谱根目录」把图片上传到项目目录（**不会自动建卷**）；不选也可以直接建空项目；
3. 进入项目 → 「新建卷」：
   - 项目有根目录时，弹窗默认「从项目根目录选择」，列出检测到的**一级子目录（每个子目录 = 一个卷，显示图片数/是否已建卷）**，勾选后「创建选中卷」；
   - 也可以切换「上传新文件夹」，按卷单独上传图片创建；
4. 识别完成后卷卡片出现「进入审阅」→ 逐页核对/改字/单列重识别/恢复上一版/重新对位 → 「完成本卷」；
5. 「导出文字」下载 txt（按列/按行两种）。

> 真实识别需要在「模型配置 → OCR 文字识别（百度）」里配置 Key；未配置时建卷/开始识别会提示去配置，图片与页记录仍会保留。
> 老库（如果有旧版 OCR 数据）：执行 `sql/migrate_ocr_standalone.sql` 或直接重启服务自动补列；旧版「项目级聚合任务」不再读取，如需迁移历史数据按本方案第 5 节脚本处理（当前本机 OCR 数据为 0 行，无迁移负担）。

# 1. 结论

**现状**：OCR 不是一条独立任务链，而是「图片处理项目的下游聚合器」。

- 一条 `ocr_tasks` 业务上是**一个项目**（不是一卷），`source_task_id` 是 NOT NULL 的遗留强绑定；
- 页不是 OCR 自己的，而是从「图片处理卷 `status='completed'` 且 `task_images.result_path` 存在的页」里**拷贝出来的路径快照**；
- 识别时每次都**实时回读** `task_images.result_path`，图片处理里改参数、重裁剪、标未通过、删结果，都会让 OCR 的图变、定位错或直接报错；
- 前端新建 OCR 只能**选一个图片处理项目**，按卷「开始 OCR」按钮只在页已并入后出现；删图片处理项目会**级联删掉 OCR 项目**。

**目标（v1.1 修订后）**：OCR 是完全独立的功能，与图片处理**没有任何数据关系**；流程与图片处理的"建项目 → 建卷"逻辑一致，建卷后直接进入 OCR 文字识别：

```
建项目（ocr_projects，独立表） → 建卷（ocr_tasks 一条=一卷，导入图片）
   → OCR 文字识别（直接用原图，不做二值化/预处理） → 进入审阅 → 导出
```

- **项目**：新建 `ocr_projects` 表，字段与 `projects` 对齐（名称/姓氏/描述/根目录），建项目、根目录自动建卷、重扫等**逻辑照搬图片处理**；
- **卷**：`ocr_tasks` 一条 = 一卷，自带图片来源目录（`source_folder`），卷与页都只引用 OCR 自己的图片；
- **页**：`ocr_pages.source_path` = 导入的原图，`image_path` = 识别/审阅所示图（**直接等于原图，不生成二值化图**）；
- **识别**：百度文字识别直接读原图；`layoutPage` 内部只做灰度墨迹投影来摆放字框（不改图、不落盘），定位失败时回退均分布局（现有逻辑）；
- **审阅**：沿用 `OcrReviewWorkbench`，去掉所有「图片处理里改过 / 未通过 / 图已更新」跨链路提示与卷过滤；
- **导出**：接线已有 `GET /ocr-tasks/:id/export`（前端已备好 URL 但没接按钮）。

**数据现状（2026-11-18 核查本机库）**：`ocr_tasks = 0 行`、`ocr_pages = 0 行`（`projects=2`、`tasks=7`、`task_images=56`）。
因此可以按**全新表结构直接改造**，不需要数据迁移；如其它部署已有 OCR 数据，按第 5 节迁移脚本处理。

## 2.1 概念对照

| 层级 | 现状 | 目标 |
|---|---|---|
| 项目 | `projects` 由图片处理独占；OCR 只能"挑一个图片处理项目" | **独立 `ocr_projects` 表**，OCR 自建自管 |

## 2.5 现状流程图（文本）

```
图片处理：
  项目(projects) → 卷(tasks) → 原图(task_images.source_path)
      → 算法/AI 处理 → 结果图(task_images.result_path) → 审阅 → 导出
      ↓ 卷 status='completed' 且结果图存在
OCR（现状，寄生在下游）：
  选一个图片处理项目 → 建一条 ocr_task（全项目聚合）
      → 自动/手动并入已完成卷的页（image_path = 结果图路径）
      → 识别（每次都回读结果图；图变/未通过/被删 → 报错或提示）
      → 审阅（可只审某卷）→ 全部确认 → 完成
```

# 3. 目标设计

## 3.1 数据模型

```
ocr_projects（新增，独立表，字段对齐 projects）
  └─1:N─ ocr_tasks（OCR 卷 = 一卷一条识别任务）
           └─1:N─ ocr_pages（OCR 页：source_path 原图 + image_path 识别图 + data_json 结果）

（OCR 侧不再引用 projects / tasks / task_images）
```

## 3.6 为什么独立项目表、不共享 `projects`

| 维度 | 独立 `ocr_projects`（采纳） | 共享 `projects`（v1.0 方案，已否） |
|---|---|---|
| 业务耦合 | 完全独立，两套功能互不影响 | OCR 项目会出现在图片处理项目列表、共享删除级联 |
| 删除行为 | 删图片处理项目/卷不影响 OCR；反之亦然 | 删图片处理项目会连带删 OCR（现 `tasks.service.ts:524-528`） |
| UI | OCR 侧独立"项目"概念，与图片处理并列 | 项目列表混用，需要额外 kind 过滤 |
| 成本 | 多一张表 + 一套项目 CRUD（逻辑照搬，成本低） | 省一张表，但耦合语义长期难维护 |

结论：**独立表**。同时必须删除 `tasks.service.ts:524-528` 的 OCR 级联删除（否则 `project_id` 在 `projects` 与 `ocr_projects` 两个 id 空间混用会误删数据）。

5. **识别直接用导入原图，不生成二值化/白底黑字中间图**（磁盘上无此类文件）。
6. 审阅页能显示原图、逐字编辑、单列重识别、恢复上一版、重新对位、全文总览；无「图片处理里改过/未通过」等提示。
7. 全部页确认后可「完成整本」；导出按钮能下载 txt（按列/按行两种模式）。
8. 删 OCR 卷/项目只清 OCR 数据与输出目录；删图片处理项目/卷、改处理结果，均不影响 OCR。
9. 浏览器刷新/深链 `/ocr/:id/review` 正常；返回任务中心位置正确。
10. 图片处理主流程回归：建项目→建卷→处理→审阅→导出无变化。
